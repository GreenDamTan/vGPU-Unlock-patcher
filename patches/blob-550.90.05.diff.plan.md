#### H. 当前已确认的业务语义起点

以下内容是已经能够从源码与 IDA 双方提炼出的“业务语义起点”，后续正式报告必须围绕这些语义展开，而不是只停留在字节/指令层。

##### 1) `_nv046497rm` 对应的是 software runlist scheduler 的运行时配置逻辑

结合 `drivers/resman/src/physical/gpu/fifo/objsched.c:3726-3817` 与 `drivers/resman/src/physical/gpu/fifo/objschedmgr.c:935-968`，当前已可确认：

- `schedMgrSwrlSetCountMax_IMPL()` 会遍历有效 runlist，并把 `swrlCountMax` 下发给 `schedSwSwrlSetCountMax()`
- `schedSwSwrlSetCountMax_IMPL()` 负责真正修改 software runlist scheduler 的“最大虚拟 runlist 数量”与相关 timeslice 配置
- 业务上，这不是一个普通调试函数，而是 software scheduling / runlist 配置链路中的实际运行时控制点

因此，正式报告在分析 `0x0047CBB7`、`0x0047CC70`、`0x02EADC58` 时，必须解释：

- `swrlCountMax` 在 scheduler 中控制什么
- 为什么源码里原本禁止“在 SWRL 正在运行时修改 count max”
- 修改该限制对运行中软件调度器意味着什么
- timeslice 计算与 `swrlCountMax` 的关系为何构成业务影响

##### 2) `_nv046497rm` 相关 patch 的业务变化不只是“分支改了”，而是“运行时策略限制被放宽”

根据当前已确认的反编译与源码：

- 原始源码语义：
  - 如果 `pSchedSw->swrlCount != 0`，则打印
    - `NVRM: Can't change software runlist max count.`
  - 并返回 `NV_ERR_INVALID_STATE`
- 这表明原始业务规则是：
  - **software runlist scheduler 一旦已经在运行，就不允许动态修改最大虚拟 runlist 数量**

结合当前 patch 字节形态，正式报告中必须重点确认并说明：

- patch 是否实际把这条“运行中不可修改”的保护逻辑绕开
- patch 前：调用方会因状态不合法而失败
- patch 后：调用方是否能够在 scheduler 已运行时继续修改 `swrlCountMax`
- 这种变化会不会影响：
  - 调度时序
  - runlist 布局
  - timeslice 分配
  - 运行中 VM / vGPU 的公平性或稳定性

##### 3) `.rodata` patch 需要按“可观测性变化”来分析

当前已确认：

- `0x02EADC58 -> 0x02EADC18` 命中的是字符串尾部 `count.\n\0`
- 它位于 `_nv046497rm` 使用的日志字符串区域
- `0x0047CC70 -> 0x0047CC30` 同时修改了原本给 `nv_printf` 准备参数的代码

因此，正式报告不能把这个 `.rodata` patch 当作孤立字符串改动，而必须解释：

- 字符串 patch 是否是在配合代码 patch 改变日志格式
- 原始日志输出表达了什么
- patch 后日志是否改成携带更多上下文（例如当前值 / 目标值）
- 即使该路径后续可能变成弱可达或不可达，也要说明它在“错误诊断/调试可观测性”上的潜在含义

##### 4) `_nv032674rm` 很可能是某种“设备支持 / 特性支持”布尔判定函数

虽然目前还没有源码级 100% 锚定，但从反编译可见：

- 函数内部存在大量按设备 ID / 子设备 ID 的白名单或特判逻辑
- 返回值语义接近布尔量
- 它被 `_nv026411rm` 调用，并直接影响后续状态位聚合路径
- 它的语义特征与 `drivers/resman/src/kernel/virtualization/grid/grid_features.c:isGridLicenseSupported()` 存在较强相似性，需要在正式分析中重点对比

因此，正式报告中必须把 `0x000D65A4` 这组 patch 作为“业务开关”类 patch 来审视，重点回答：

- patch 是否把原本依赖设备白名单/平台状态的支持判定强行改成恒成立
- 若恒成立，被放开的到底是：
  - vGPU software licensing 支持判定
  - 某类 GRID feature 支持判定
  - 或更底层的 capability gate
- patch 前后，哪些本来不应通过的 GPU / SKU / 配置可能被视为“支持”

##### 5) `_nv026411rm` 应按“能力探测结果聚合”来写报告

当前已确认：

- `_nv026411rm` 会调用 `_nv032674rm`
- 还会调用 `_nv026628rm` 以及若干函数指针回调

因此，正式报告中不能只写“它设置了一些字节”，而必须尽量解释：

- patch 前后，这条聚合链会让后续上层逻辑认为 GPU 具备了哪些能力 / 许可 / 支持状态
- 哪些调用方或控制命令可能直接消费这些状态

##### 6) 报告必须显式区分“已确认业务事实”和“待验证业务推断”

本次 patch 业务分析里，至少有两类内容：

- **已确认业务事实**
  - 例如 `_nv046497rm` 命中 `objsched.c` 的 runlist/timeslice 控制逻辑

## 3.4 后续版本快速定位与 patch 复用指南

最终正式报告必须单独包含一节“后续版本快速定位与复用指南”，用于回答：

该章节不能只给抽象建议，必须提供可执行的方法。至少应包含以下内容：

### A. 多层定位锚点表

对每个 patch 点都要总结可迁移到新版本的定位锚点，按稳定性分层。

**重要约束：正式报告必须明确说明，函数名（如 `_nv026411rm`）和源码相对路径在后续版本中都可能变化，因此它们不能作为主要定位方法，只能作为当前版本的解释性标签或辅助对照。**

推荐锚点优先级应写成：

1. **字符串锚点**
   - 例如：
     - `NVRM: Can't change software runlist max count.`
     - `NVRM: Software scheduler timeslice set to %duS.`
   - 要说明字符串是否可直接 xref 定位，还是只适合作为辅助线索
2. **控制流锚点**
   - 关键判断、关键返回值、关键 basic block
   - 例如“运行中禁止修改 `swrlCountMax` 的保护分支”“设备 ID 白名单判定块”“状态位写回块”
3. **调用链锚点**
   - 例如：
     - `schedMgrSwrlSetCountMax_IMPL -> schedSwSwrlSetCountMax_IMPL`
     - “状态聚合函数 -> 设备白名单判定函数”
   - 报告中应优先描述调用职责，而不是只写当前版本函数名
4. **结构/状态写回锚点**
   - 例如连续状态字节写回
   - 关键对象字段偏移读写模式
   - 多个 capability 位聚合后的布尔结果构造方式
5. **源码锚点**
   - 对应函数职责
   - 源码相对路径
   - 关键控制条件
   - 仅作为“有源码时的加速器”，不是无源码场景下的主定位方法
6. **字节/汇编锚点**
   - 只能作为最后一级锚点
   - 需要强调：跨版本时不能只靠几字节硬搜，必须结合函数语义校验

### B. 后续版本的推荐定位顺序

**正式报告必须明确声明：后续版本定位不能依赖自动命名函数名，也不能把源码存在当成前提。**

也就是说，下列信息：

- `_nv026411rm` / `_nv032674rm` / `_nv046497rm` 这类 IDA 自动命名
- `schedSwSwrlSetCountMax_IMPL` / `isGridLicenseSupported()` 这类源码函数名
- 具体源码路径

都只能作为当前版本的解释性对照或“有源码时的加速器”，**不能作为后续版本主定位方法**。

正式报告必须给出推荐的实操顺序，并区分两条路径：

#### 路径 1：只有 IDA / 只有二进制时

1. 先用字符串窗口和字符串 xref 缩小范围
2. 再用控制流形状定位关键保护分支 / 状态聚合块 / 日志参数准备块
3. 再用调用关系识别“聚合函数 -> 判定函数”这类职责链
4. 最后才用字节特征做兜底确认

#### 路径 2：同时有源码与 IDA 时

1. 先从源码提取职责线索、日志字符串、关键条件和错误码
2. 再回到 IDA 中通过字符串、控制流和调用关系定位
3. 最后把源码映射作为语义确认，而不是主定位手段

对当前已知 patch，至少要明确写出：

- software runlist scheduler 这组点，优先从两条日志字符串、错误返回路径、timeslice 设置路径入手，而不是先依赖当前函数名
- 设备支持/特性判定这组点，优先从“大量 device ID / subdevice ID 条件分支 + 布尔返回值”的控制流形状入手，而不是依赖 `_nv032674rm` 这个名字
- 状态聚合这组点，优先从“调用一个判定函数后回填一组连续状态字节”的模式入手，而不是依赖 `_nv026411rm` 这个名字

### C. 在 IDA 中快速定位的明确方法

正式报告必须**明确写出在 IDA 中如何快速定位这些 patch 点**，不能只写“可通过字符串/调用链定位”，而要写成可执行步骤。建议至少覆盖以下方法：

#### 方法 1：通过旧版本 diff 偏移直接落点

适用于当前已分析版本。

步骤应写清：

1. 先确认当前打开的二进制就是目标 `nv-kernel.o_binary`
2. 核对 hash 是否与 `blob-550.90.05.diff` 第一行一致
3. 按本文已确认的映射关系计算：
   - `IDA_EA = DIFF_OFFSET - 0x40`
4. 直接跳到对应 EA
5. 用 `get_bytes` / `disasm` 验证该位置字节是否与 diff 中“旧字节”一致

正式报告中必须给出至少这些已知样例：

- `0x000D65A4 -> 0x000D6564`
- `0x0047CBB7 -> 0x0047CB77`
- `0x0047CC70 -> 0x0047CC30`
- `0x0051DDDB -> 0x0051DD9B`
- `0x02EADC58 -> 0x02EADC18`

并明确说明：这种方法**只适合当前版本或极近版本**，版本变化后偏移可能失效。

#### 方法 2：通过字符串 xref 快速定位 `_nv046497rm` 这组 patch

这是后续版本中最值得优先推荐的方法之一。

正式报告必须写清以下 IDA 定位路线：

1. 在 IDA 字符串窗口搜索：
   - `NVRM: Can't change software runlist max count.`
   - `NVRM: Software scheduler timeslice set to %duS.` 或接近字符串
2. 对字符串查看 xrefs
3. 沿 xref 回到引用点
4. 进入引用所在函数，即 `_nv046497rm` 对应逻辑
5. 再在该函数内定位：
   - 运行中禁止修改 `swrlCountMax` 的错误返回路径
   - timeslice 设置完成后的日志打印路径

正式报告中还要说明当前版本已验证的 xref 样例：

- `0x47CC36 -> "NVRM: Can't change software runlist max count.\n"`
- `0x47CBF1 -> "NVRM: Software scheduler timeslice set to %uuS.\n"`

并提示：如果字符串文本在新版本中有轻微变化，应优先搜关键词：

- `software runlist`
- `timeslice set`
- `count max`

#### 方法 3：通过“状态聚合函数 -> 支持判定函数”的调用职责定位

这是后续版本里定位“能力探测/支持判定”那组 patch 的核心方法，而且**不能依赖当前版本函数名**。

正式报告必须写清以下 IDA 路线：

1. 先在 IDA 中寻找一个具有下列特征的“状态聚合函数”：
   - 会调用多个子判定函数或函数指针回调
   - 会写回一组连续状态字节/标志位
   - 会把多个布尔判定结果聚合成最终 capability / feature state
2. 查看其 callees，确认是否存在一个“设备白名单 / 支持判定”函数：
   - 内部包含大量 device ID / subdevice ID 条件分支
   - 返回值语义接近布尔量
3. 沿该调用进入候选判定函数
4. 在被调函数中确认：
   - 是否存在大量 device ID / subdevice ID 判定
   - 是否以布尔/状态值形式返回结果
   - 是否存在用于放行/拒绝特定 SKU 或配置的集中分支
5. 再回到聚合函数，确认其如何消费这个返回值并写回状态字节

正式报告中应写明当前版本已验证的“当前版本样例”，但必须同时注明这些名字未来可能变化：

- 当前版本样例中，状态聚合函数会在 `0x51DE43` 调用一个设备支持判定函数
- 当前版本样例中，状态聚合函数还会调用 `_nv026628rm` 等辅助判定逻辑，并回填连续状态字节
- 报告必须把这条链路描述为“职责模式”，而不是把 `_nv026411rm -> _nv032674rm` 当成跨版本稳定标识

#### 方法 4：通过源码职责反推到 IDA（仅作为加速器）

这是“有源码时最快”的版本迁移方法，但正式报告必须明确写出：**它只是加速器，不是前提条件。**

应至少说明：

1. 若有源码，可先在源码中定位业务函数职责
   - 如 software runlist count/timeslice 配置逻辑
   - 如 device support / license support 判定逻辑
   - 如 capability state 聚合逻辑
2. 提取源码中的稳定锚点：
   - 日志字符串
   - 关键错误码
   - 关键条件判断
   - 关键调用关系
3. 再回到 IDA 中用这些锚点定位对应函数
4. 最后确认 patch 点是否仍然处于同一业务块内

同时必须补一句说明：如果没有源码，仍可按“字符串 -> 控制流 -> 调用职责 -> 字节确认”的顺序完成定位。

#### 方法 5：通过 basic block 和控制流形状二次确认

正式报告必须强调：**在 IDA 中找到疑似位置后，不能立刻下结论，必须再做控制流确认。**

至少要检查：

- 命中地址是否位于预期的 basic block
- 该 block 的前驱/后继是否仍对应旧版本业务流程
- patch 改动的是：
  - 保护性 early-return
  - 条件跳转
  - 日志参数准备
  - 状态位写回
  - 还是返回值构造

对 `_nv046497rm` 这组点，报告中要明确写出：

- `0x47CB77` 的命中 block 是 `0x47CB60 - 0x47CB7F`
- `0x47CBB7 - 0x47CBD8` 是同函数中的后续独立 block，只能作为关联路径，不是同一个命中块

#### 方法 6：通过字节特征做最后一级兜底定位

正式报告必须说明：

- `find_bytes` 只能作为最后一级兜底方法
- 必须先有函数语义或字符串/调用链锚点，再用字节特征确认
- 不能在新版本里仅凭 4~8 字节命中就认定 patch 点一致

可写入报告的当前版本样例包括：

- `0x47CB77`: `85 ED 0F 85 B1 00 00 00`
- `0x47CC30`: `41 BD 40 00 00 00 48 C7`
- `0x51DD9B`: `85 C0 74 07 C7 45 0C 00`
- `0xD6564`: `41 56 41 55 53 48 83 ED`

但报告必须同时提醒：这些字节模式跨版本可能变化，应以“语义一致”优先于“字节一致”。

### C. 新版本复用时的语义一致性检查清单

正式报告必须给出“找到疑似 patch 点之后如何验明正身”的清单。至少包括：

1. 这个函数的职责是否和旧版本一致
2. 关键字符串 / 日志是否仍一致或仅小改
3. 关键分支条件是否仍表达同一业务规则
4. 关键返回值 / 错误码语义是否一致

6. patch 后改变的行为是否仍对应同一个业务目标

### D. 复用判定结果的分类标准

正式报告中应给出以下三种结论类型，供后续版本移植时直接套用：

- **可直接复用**

- **需要重定位后改写**
  - 业务位置相同，但具体分支、寄存器或指令布局不同
- **不建议直接复用**
  - 上游业务逻辑已变化，直接套旧 patch 可能引入副作用

## 4. 计划中的实际分析步骤

## 步骤 1：解析 `blob-550.90.05.diff`

目标：先把 patch 文件本身拆开，建立 hunk 清单。

- 统计 hunk 数量

- hunk 索引表
- 每个 hunk 的基础字段清单

## 步骤 2：在 IDA 中定位 patch 命中地址

目标：把每个 hunk 从 diff 偏移映射到 IDA 里的具体地址。

需要完成：

- 确认当前 IDA 实例与目标二进制一致，优先核对当前打开对象是否为 `nv-kernel.o_binary`
- 获取 image base、segments、模块元数据
- 记录 `nv-kernel.o_binary` 在 IDA 中的装载信息，作为后续地址映射基准
- 将每个 hunk 对应到 IDA 地址

输出物：

- hunk -> IDA 地址映射表
- 所属函数初步清单

## 步骤 3：提取每个 hunk 的 IDA 证据

目标：为每个 hunk 采集足够的逆向证据。

需要完成：

- 找到最可能的源文件相对路径与行号
- 提取必要源码节选
- 对每个映射打上置信度标签

置信度建议分级：

- **高置信映射**：控制流、常量、调用关系和语义都能稳定对上
- **中置信映射**：核心语义能对上，但局部细节或命名存在偏差
- **推测映射**：只能根据局部模式和业务语义推断，缺少足够直接证据

输出物：

- hunk -> 源码相对路径/行号/节选/置信度表

## 步骤 5：解释 patch 前后逻辑变化

目标：把“字节改动”翻译成“业务逻辑变化”。

需要完成：

- 判断是否改变了条件跳转方向
- 判断是否强制让某个条件恒真/恒假
- 判断是否修改了返回值或错误码

输出物：

- 每个 hunk 的 patch 前后行为对比说明

## 步骤 6：整理整体影响与关联关系

目标：把单点分析整合为完整故事线。

需要完成：

- 识别多个 hunk 是否共同服务于同一业务目标

输出物：

## 5. 证据采集与展示规则

为了保证正式文档可复查，计划采用以下证据规则：

### 5.1 源码引用格式

统一写成：

- `relative/path/to/file.c:123-145`

并附必要代码节选。

### 5.2 IDA 引用格式

每处关键证据尽量包含：

- 函数名
- 函数起始地址
- hunk 命中地址
- 关键 basic block 地址

### 5.3 汇编引用格式

汇编节选必须带地址，例如：

```asm
0xXXXXXXXX  test ...
0xXXXXXXXX  jnz  ...
0xXXXXXXXX  mov  ...
```

### 5.4 伪代码引用规则

只节选与 patch 直接相关的局部逻辑，不默认贴整函数；除非该函数本身很短，或者整函数上下文对理解 patch 必不可少。

### 5.5 结论表达规则

每个分析结论都要尽量区分：

- 直接证据
- 关联证据
- 推断结论

不能把“推测”写成“事实”。

## 6. 重点检查项

正式分析时，应默认检查以下问题，避免遗漏：

1. patch 是否改动条件跳转方向
2. patch 是否强制某个分支恒成立或恒不成立
3. patch 是否修改返回值或错误码
4. patch 是否改写 capability / mode / policy 判定
5. patch 是否绕过某种校验、兼容性限制或签名检查
6. patch 是否影响结构体字段、全局变量或状态位
7. patch 是否只影响单函数，还是影响整条调用链
8. patch 是否可能引入副作用或兼容性问题

## 7. 风险与不确定性处理策略

在正式分析过程中，可能出现以下情况：

### 7.1 二进制与源码并非一一直接对应

如果 `stage_rel` 中的源码与当前 blob 版本存在命名差异、内联差异、宏展开差异或编译器优化差异，则不能只靠函数形状简单断定对应关系。

处理方式：

- 结合控制流、常量、日志、调用关系和业务语义综合判断
- 对每个源码映射打置信度标签
- 对不确定处明确写出理由

### 7.2 某些 hunk 可能落在缺少符号信息的区域

处理方式：
